## 1. Executive Verdict

- The proposal’s core current-state picture is correct: JSON files, no database, no CA table, scores computed in memory, AI replies not stored as product audit records.
- The hard Phase 1.75 constraints are justified: keep raw CSV OHLCV, do not treat vendor change/changePercentage as truth, keep live last distinct from CSV close, do not feed unadjusted long windows as research-grade history.
- The proposed identity + mapping + raw bars + CA + validation + fundamentals core matches what the repo actually needs for Phase 2 adapters.
- Several items classified REQUIRED NOW / REQUIRED SOON are not required for the first persistence increment: exchange, full trading_calendar, adjustment_run + materialized ohlcv_bar_adjusted, and the four AI version tables.
- Current production already has a split-brain serving model: GitHub Pages can serve Mubasher/market-snapshot.json, while Render builds with PRICE_SOURCE=yahoo. Dual-write design must account for that, not only “Vue reads files / API reads files.”
- Live overlay is stronger than the proposal states: if the last CSV day is not Cairo “today,” fetchMubasherQuote appends a today-dated live bar. Weekend scrapes can invent a non-session bar.
- mubasher-integrity.json does not contain the COMI 2025-12-16/17 split rows. That split is documented in Phase 1.75 text, not in the committed JSON artifact.
- PostgreSQL + JSONB vs MongoDB: neither is in the repo. For this domain, relational uniqueness/FKs are the concrete advantage; MongoDB does not solve a problem JSONB does not. This is evidence, not a platform decision.
- Do not implement schema yet. Blocking decisions remain: store, canonical close, whether Phase 2 computes adjusted series, duplicate-bar policy, license, and whether AI audit is in the same increment.

## 3. Domain Invariants

These are the invariants a future store must guarantee. They are derived from repo behavior and Phase 1.75/1.5 evidence, not from generic database advice.

1. Raw vendor OHLCV is immutable. CSV (and Yahoo chart) prints must never be overwritten by split/dividend restatement, live last, or a later provider revision. Evidence: Phase 1.75 blocker; parseCsvCandles has no adjClose; COMI pre-split closes stay on old scale in the Phase 1.75 TESTED table.

2. Live last and session/CSV close are distinct facts. bar.value and CSV c differed on 14/16 names. quote.price today is live last after overlay (mubasherQuote.js L143, L165, L176). Persisting only one “close” destroys auditability (Phase 1.75 condition 1).

3. Overlay must not destroy the CSV last bar. Current code replaces or appends in the in-memory candle array (mubasherQuote.js L168–169). Persistence must store CSV close and live last, with an explicit overlay flag and the Cairo session date actually being overlaid — not “today” if today is not a session.

4. Provider symbol is not canonical instrument identity. In-app id is TICKER.CA (data/symbols.js, normalizeTicker in server.js L79–85). Mubasher uses stripped Reuters-like codes (mubasherCode). Yahoo may use yahoo: overrides including ISINs and EKHO.CA. EODHD/Twelve conventions exist only in docs (COMI.EGX, EGS60121C018). Mapping rows must not collapse these into one string.

5. Vendor change / changePercentage are untrusted. Failed independent calc on 10/16 and 12/16 (PHASE_1_75 §7; JSON changeCheck). They may be stored as vendor-supplied fields, never as the computed return used by scores or AI as ground truth.

6. Corporate actions are independent events, not bar mutations. Mubasher CSV has no split/dividend flag. A 1.1 split is a separate fact. Unknown jumps (2008 spike-revert in JSON) must not be auto-written as splits.

7. Adjusted series, if computed, is derived and versioned. Reproducible from: raw bars + a frozen CA set + a named method version. Until dividends/full CA calendar are known, any adjusted series is incomplete (PHASE_1_75 §9). It must never become the only stored tape.

8. Duplicate session dates must be handled deterministically. Integrity counted 4–5 duplicate dates per CSV. Unique (instrument, provider, session_date) will fail unless first-wins / last-wins / keep-with-sequence is defined before schema.

9. Invalid OHLC must not become trusted market data. Hundreds of open-outside-high/low flags per name (Phase 1.75 §8). Ingest may store them as raw, but validation must mark them; indicators must not treat them as clean.

10. RANGE-filtered files are not the historical archive. latest.json / market-snapshot.json hold range candles (default 3mo). Full CSV exists only at the provider URL. Migration cannot treat current JSON as 25y history (PHASE_2A §17.4 is correct).

11. Validation results are first-class, not log-only. Phase 2 gate is adapters/validation, not “fix the CSV.” Failures (last≠close, change mismatch, duplicates, jumps, CA-unadjusted windows) must remain queryable.

12. Provider payload provenance is required where a number is later disputed. Re-parse and license audit need the quote JSON / CSV text if the architect allows storing them (license UNKNOWN). Normalized columns alone cannot explain a later vendor change.

13. Historical snapshots must remain interpretable after providers change. data_snapshot.price_source, mapping verification_class, and scrape scraped_at are part of meaning. Render Yahoo vs Pages Mubasher already demonstrates two tapes for the same ticker.

14. Scores/indicators are derived from a declared series. analyzeQuote has no series kind. Feeding unadjusted max-history across a known split contaminates EMA/RSI/MACD/score (indicators.js L427; Phase 1.75 §9). Derived output must record whether input was raw or adjusted.

15. AI decisions, if audited, are reconstructable from the exact input sent, not from later market files. /api/suggest sends truncated raw candles (60/90) and live Mubasher HTML fundamentals; /api/ask sends scored compactForAi slices. A later CA backfill must not rewrite those inputs. Keys must never be stored (useAiSettings.js).

16. Model / prompt / score identity is required for audit, not as three mandatory tables. Defaults and inline templates exist (gpt-4o-mini, composer-2.5, prompts in server.js). Capturing provider+model+prompt hash+git SHA of indicators.js at call time is the invariant; table shape is secondary.

17. Fundamentals are a separate as-of snapshot, not a property of the last price bar. File can be days stale (fundamentals.json 2026-08-17 vs tape 2026-08-20). PE/EPS period type is UNKNOWN. Negative PE already exists outside the 16-name sample (AALR pe: -13.26 in committed file).

18. Client secrets and fund holdings stay off the server store unless product scope changes. egx-ai-settings, egx_auth_session, egx-my-funds-v1 are browser-only.

19. EGX session date is Africa/Cairo, not scrape wall-clock. CSV timestamps are parsed as T00:00:00+02:00 (mubasherQuote.js L54) while dayKeyCairo uses Africa/Cairo (L67–68). DST vs fixed +02:00 is an INFERRED risk (proposal §20.13). Bars must key by Cairo session date, not UTC scrape date.

20. Unadjusted long history must not be labeled research-grade or used as Phase 4 backtest input. Phase 1.75 Phase-2 gate: YES adapters/validation; NO history-as-truth across CAs.

## 5. PostgreSQL + JSONB vs MongoDB

Comparison is against this repo’s requirements only. Neither engine exists in the project. Volume figures are INFERRED from 16-name CSV depths, not a production census of 224 names.

| Requirement | PostgreSQL + JSONB | MongoDB | Evidence from this project |
|---|---|---|---|
| EGX instrument identity | Strong unique/FK story for one instrument, many codes | App-enforced uniqueness; easier to store duplicate COMI/COMI.CA as separate docs | Identity is already split across ticker, yahoo, mubasherCode |
| Multi-provider symbol mapping | Native unique (provider, provider_symbol, valid_from) | Unique indexes possible; no FK to instrument | Phase 1.5 table; 17 Yahoo overrides |
| Daily OHLCV | Relational uniqueness; date range SQL | Fine with compound indexes | ~1k–6k bars/name in sample; 224 names → order 10^5–10^6 rows if full CSV stored — not a scale argument against PG |
| Corporate actions | Typed events + FK to instrument; join to bars by ex_date | Possible; CA application is application code | Blocker is integrity, not throughput |
| Raw vs normalized vs adjusted | Separate tables + permissions/CHECK | Separate collections + discipline | JSON files cannot enforce “never overwrite raw” |
| Validation results | JSONB payload + pass/fail columns | Natural documents | Trees already look like mubasher-integrity.json |
| Fundamentals | Sparse JSONB + extracted PE/EPS | Natural documents | fundamentals.json is already a document |
| AI decision snapshots | JSONB + TOAST | Natural documents | Prompt blobs are large; either works |
| Versioning | FKs to version rows or hash columns | Embed hashes in the document | Current need is hashes, not a version graph |
| Historical reconstruction | Snapshot row + FK to then-current mapping/CA set | Embed context document (easier point-in-time blob) | Reconstructability depends on what you store, not engine |
| MVP scale | Low millions of daily bars is ordinary | Also ordinary | No repo evidence of write volume beyond ~224 quotes / 20s watch |
| Node/Vue architecture | Needs a query layer or keep exporting JSON | Same | Vue reads static files (useMarketData.js); API is node:http (server.js) |
| Render + GitHub Pages | Managed PG is an ops decision (Render free web in render.yaml has no database) | Same | Dual-write latest.json remains if Pages stays file-based |

A. Where PostgreSQL gives a concrete architectural advantage

- Enforcing one instrument, unique provider symbols, and CA rows that cannot dangle.
- Making “raw bar row is not updated” a schema/permission rule rather than a convention.
- Joining CA ex_date to raw bars without embedding CA inside every candle document.
- Preventing two mappings from silently pointing at different instruments for the same provider symbol.

B. Where MongoDB gives a concrete architectural advantage

- Storing heterogeneous vendor payloads and AI prompt/context blobs with less schema work.
- Point-in-time snapshot documents (input_context + output) match how latest.json already looks.
- No migration/ORM ceremony for a team that today only writes JSON files.

C. Whether MongoDB solves any problem PostgreSQL + JSONB does not

- No, for this domain. JSONB covers vendor payloads, validation trees, fundamentals leftovers, and AI blobs. MongoDB’s document comfort does not restore CA integrity, last-vs-close, or mapping uniqueness.

D. Integrity problems MongoDB would push into application code

- Instrument uniqueness across Reuters / .CA / ISIN / .EGX.
- ohlcv_bar immutability vs “just replace the document.”
- Duplicate CSV dates (must still be a written policy).
- Referential link from adjusted series → raw bar + adjustment method + CA set.
- Orphan validation results and CA rows after symbol remaps.

E. Whether projected volume is a reason to avoid PostgreSQL

- No evidence that it is. 16 names × up to ~6k rows; 224 names even at 6k is ~1.3M rows. Watch currently overwrites one JSON file, not a bar warehouse. Volume is not the decision driver; identity + CA + overlay semantics are.

Not a platform decision. If a database is approved, the domain argues for a relational core. If the architect prefers Mongo, the same invariants must be implemented in application code. JSON files cannot carry them.

## 7. Missing Architectural Decisions

### Blocking

Decisions that must exist before schema implementation:

3. Phase 2 computes adjusted series vs CA storage only. Proposal §15 and §22.3 conflict in emphasis with §5/§10. Must be explicit.

5. Live overlay representation: two raw rows (csv + live_overlay) vs quote-level last + immutable CSV bars. Must also decide what happens when Cairo today ≠ last CSV session (append-today is current behavior).

## 8. Minimal Conceptual Architecture

Smallest persistence that could satisfy Phase 2 (adapters / validation / CA-safe contract), without implementing it:

RAW → NORMALIZED → CORPORATE ACTIONS → ADJUSTED → DERIVED → AI AUDIT

### RAW

- Belongs: vendor quote JSON (optional, license-gated); CSV text or parsed CSV OHLCV exactly as printed; Yahoo chart quote[] if used; vendor change/changePercentage labeled untrusted; scrape errors.
- Never mix: adjusted prices, live last overwriting CSV c, indicator scores.
- Source of truth: the provider payload for that fetch (Mubasher CSV URL / Yahoo chart body).
- Versioning: provider, fetch scraped_at, source URL, optional payload hash. No updates in place.

### NORMALIZED

- Belongs: instrument id; resolved mapping; Cairo session_date; typed OHLCV from RAW; quote last as a separate field from csv_close; currency EGP; source_kind (csv | live_overlay | yahoo_chart); data_snapshot (range, price_source, error_count); fundamental_snapshot as-of; data_validation_result.
- Never mix: CA-restated values; treating change% as computed return; treating fundamentals as same-session as prices without as-of.
- Source of truth: RAW + mapping tables.
- Versioning: snapshot id; mapping verification_class (TESTED | DOCS | INFERRED); do not silently remap history.

### CORPORATE ACTIONS

- Belongs: split/bonus/dividend/rights/unknown_discontinuity events; ex_date; ratio or cash; citation; confidence.
- Never mix: bar patches; inferred-only jumps stored as verified splits.
- Source of truth: cited external CA (today: COMI 1.1 2025-12-17 in Phase 1.75) plus later vendor/manual policy.
- Versioning: event id; source/citation; confidence. Adding a CA later must not rewrite RAW.

### ADJUSTED

- Belongs: (later) series produced from RAW + a frozen CA set + method version.
- Never mix: writing back into RAW; serving as the only close in the UI without an architect decision; calling it complete while dividends UNKNOWN.
- Source of truth: RAW + CA set + method. If this layer is empty in Phase 2, that is acceptable if indicators are not claimed research-grade.
- Versioning: method_version + ca_set_hash. Recompute, don’t update.

### DERIVED

- Belongs: EMA/RSI/MACD/score/depth/sector heuristics.
- Never mix: storing derived close as market data; mixing last-trade and csv-close in one series.
- Source of truth: a declared series_id (raw or adjusted) + analyzeQuote implementation identity (git SHA).
- Versioning: optional. Default: recompute. Persist only for audit.

### AI AUDIT

- Belongs: (optional increment) insert-only record of endpoint, lang, provider, model id, prompt hash/text, input JSON actually sent, output JSON, market_scraped_at.
- Never mix: API keys; later-rewritten candles; assuming /api/suggest and /api/ask share the same context shape.
- Source of truth: the request/response at call time, not the current latest.json.
- Versioning: new row per call; supersedes_id if corrections exist. No UPDATE of body.

Intentionally not in this minimum: exchange table, trading calendar table, adjustment_run workflow, materialized adjusted tape, model/prompt/score catalogs, portfolio/orders, news, EGX30, backtests, dual Mongo+Postgres.

## 9. Contradictions / Ambiguities

1. REQUIRED NOW vs omitted from MVP tables — exchange. §5 classifies Exchange REQUIRED NOW. §21 recommended MVP tables list instrument/symbol/provider/mapping/snapshot/quote/ohlcv/CA/validation/fundamentals — no exchange. §9.1 still specifies exchange.

2. REQUIRED SOON vs out of MVP — trading calendar. §5 and §9.4b: Trading Calendar REQUIRED SOON. §15: “Full holiday calendar (stub timezone + weekday rule only if needed)” is out of MVP DB.

3. AI audit REQUIRED SOON vs optional increment vs omitted from MVP. §5: AI Analysis, Decision, Decision Snapshot, Model/Prompt/Score/Input Context all REQUIRED SOON. §4: snapshots only “if product claims auditability.” §15: AI snapshots “can ship immediately after ingest … otherwise second increment.” §21 MVP tables omit AI tables. Same artifact, three strengths of requirement.

4. split entity vs corporate_action.type. §5: Split REQUIRED NOW as its own entity (Bonus REQUIRED SOON, Cash Dividend REQUIRED SOON, Rights FUTURE). §10 / §21: a single corporate_action with type. Duplicate classification.

5. Adjusted series in vs out. §10 rule 2: indicators that need split-continuity consume adjusted series after adjustment_run. §15: computing/serving split-adjusted bars as the only series used by analyzeQuote is out of MVP; CA storage is in. §22.3 leaves the decision to the architect. The data model still includes ohlcv_bar_adjusted as if Phase 2 will materialize it (§9.8).

6. Overlay description vs code. §2.1: overwrite last bar if Cairo day == today. Code also appends a today-dated live bar otherwise (mubasherQuote.js L168–169). §14 “Never drop CSV close because live last exists” is a proposed rule that current persistence already violates inside latest.json.

7. Immutable snapshots vs mutable latest.json dual-write. §12: decision snapshots insert-only. §17/§18: optional dual-write continues to overwrite latest.json. If Vue keeps polling files, the file is not a snapshot; the DB row must be. Ambiguous which consumers see which close.

8. Close has three meanings already. Mubasher live bar.value → quote.price / last c; Mubasher bar.close → previousClose; CSV c → discarded on overlay; Yahoo previousClose is prior candle, not meta.previousClose. §20.1 / §22.2 still open. Any schema column named close without a qualifier will conflict.

9. Identity definitions. §2.1 inferred debt: “Identity is Yahoo ticker (COMI.CA) everywhere.” §9.2 proposes reuters_code as instrument field. §11 mapping treats Reuters / .CA / .EGX / ISIN as equal aliases. Canonical key is not chosen — listed as §22.6, but §9 already stores reuters_code as if it were canonical.

10. yahoo: overrides called ISIN-style. §2 inferred point 1: 17 yahoo: “ISIN-like” codes. Two are EKHO.CA / EKHOA.CA (data/symbols.js L1109–1118).

11. Default price source vs production. §2: PRICE_SOURCE mubasher default. render.yaml forces Yahoo for the hosted API. Pages workflow scrape uses default (Mubasher) or market-snapshot.json. “Current persistence” is not one tape.

12. Missing store in §3 table. web/public/market-snapshot.json is committed and used as Pages fallback (deploy-pages.yml L35–40). Not in §3 Current Persistence Model.

13. Tests: none vs informal scripts. §2: tests none found; UNKNOWN informal scripts. research/benchmark/mubasher-integrity.mjs is exactly that.

14. candleCache vs full CSV. §2 inferred point 4: “full CSV is discarded except in-memory candleCache.” Cache stores range-filtered candles (mubasherQuote.js L111–123).

15. Scale claim. §7: ~224 × ~25y × ~250 ≈ low millions. Sample depths vary 4.8y–25.3y (Phase 1.75 §10). 224 × 25y is an upper bound, not measured for the full universe.

16. Score 0–100 vs other clamps. §5 Score: analyzeQuote 0–100. Scalp/week paths clamp to 92 (indicators.js L258, L330, L389). A single score_version cannot describe all formulas.

17. decision_snapshot includes score_version_id for all endpoints. §12. /api/suggest explicitly does not send scores (server.js L759–760). FK would be null or misleading for that endpoint.

18. Unique ohlcv key vs current file shape. §9.7 unique (instrument_id, provider_id, session_date, source_kind) allows csv+overlay coexistence. latest.json can hold only one last bar. Dual-write without transforming overlay will not populate both kinds.

19. Phase 2 gate wording. Phase 1.75: Phase 2 must include CA handling in the data contract, not later. Proposal §15 correctly stores CA but defers adjustment-as-truth. That is consistent only if “CA handling” means storage + contract, not adjusted indicators. The document uses both senses.

20. JsonlLocalAgentStore vs “no AI audit log.” §1/§12: no immutable AI audit log. server.js L33–36 writes Cursor agent JSONL under .cursor-agents/ (gitignored). Not a product audit log, but “no persistence” is slightly too strong for the Cursor path.

21. Fundamentals news. §5 News FUTURE because pickFundamentals drops news. /api/company and AI fundamentalsForAi still fetch live news (server.js L144–147, L663). Snapshot model that only follows fundamentals.json will not match what /api/suggest actually sent.

22. Watch interval claim. §2 table: watch every INTERVAL default 20s — true for watch.js. README still says 10s / 5s poll (stale docs, not in the proposal, but hosting docs also still say Yahoo-primary).

## 10. Recommended Next Phase

Do not implement schema, adapters, dual-write, or database installs.

The architect should issue a short decision record that answers the Blocking list in §7, at least:

- store vs files-only
- canonical close
- CA storage only vs adjusted materialization
- duplicate-date and overlay representation
- validation failure policy
- license for raw payloads
- whether AI audit is in increment 1
- how Pages and Render stay on the same tape

After those decisions exist, the next research/architecture step (still not production code) should be a trimmed logical model that contains only:

instrument (thin) · provider mapping · data_snapshot · quote (last vs prev vs vendor change) · raw ohlcv_bar · corporate_action · data_validation_result · fundamental_snapshot

…and explicitly parks adjusted tape, version catalogs, and decision snapshots as increment 2+.

Optionally, a same-day identity fixture (COMI mappings + one cited split + last-vs-close example from mubasher-integrity.json) can be written as documentation to freeze semantics before any migration.

Until that decision record exists, implementing PostgreSQL or Mongo would freeze unresolved meanings of close and identity into tables.
